# Read text when the user highlights it

Enable **Dyslexia -> I prefer listening to text**, choose a local voice/speed if desired, and select **Save and apply**. Highlight ordinary webpage text with the pointer, Shift + selection keys, or Select All. Reading starts after selection settles for 250ms. No Read selection button or open settings tab is required. A new selection replaces the previous utterance. Escape, the on-page Stop button, clearing the selection, navigation, or disabling/resetting the preference stops automatic speech.

## Reading a button label without activating it

With the same listening preference enabled, point at a site button or focus it with Tab. A separate **Read button label** action appears at the bottom right. Activate that action, or press **Alt+Shift+R**, to read the current button's label. Hover/focus alone never starts speech. Escape stops reading and removes the action. Normal site clicks, Enter/Space activation, text selection and input values are left unchanged. The shortcut's default is prevented only when a current button target exists; the visible action is the alternative if the OS/site reserves the shortcut.

Supported targets are native buttons, explicitly labeled input button/submit/reset controls, and elements with `role="button"`, including dynamically added controls and reachable open shadow roots. Common accessible-name sources are read in order: `aria-labelledby`, `aria-label`, visible descendant text/image alt text, then `title`. Referenced ARIA labels may legitimately be hidden. Decorative aria-hidden or CSS-hidden descendants are ignored for the visible-text fallback. Native input buttons use their button value, never a text/password field's value. Labels are capped at 2,000 characters, reference count and traversal are bounded, and label text is collected only on the explicit read action. Missing labels produce a message; labels are not invented. This is a practical common-name reader, not the complete accessible-name specification for every custom widget.

The action is isolated in extension-owned closed Shadow DOM. It never calls the original button's click/focus method or changes its role, handlers, styles or attributes. Delegated listeners cover dynamic controls without scanning the page. Disable removes the action, status panel and listeners. A pending label reading is kept separate from native text-selection clearing, and shortcut key releases do not accidentally start reading a previously selected input. Reading uses the same local voice, language detection, rate and permission rules as selected text. Inaccessible closed-shadow internals, unlabeled icon controls, browser UI and restricted pages remain limitations.

The contract is explicit selection, not the extension's hover word/passage highlights. Programmatically changing Selection alone does not start speech. Ordinary text/search/tel/url inputs and textareas now support selection-to-speech using `selectionStart`/`selectionEnd`: only the selected substring is read. Password inputs and fields marked as password, payment-card or one-time-code autocomplete remain excluded. Email/number/date controls lack the necessary native selection API and remain unsupported, as do rich contenteditable editors. Ordinary document selections spanning protected editing controls are excluded. Text is capped at 32,768 characters and is never logged or saved. It is sent locally from the content script to the extension service worker, which selects only voices reported as local (`remote === false`). Missing voices or extension errors appear in an on-page status panel. The feature does not automatically install voices or use a remote speech fallback.

For native controls, document Selection can be collapsed even while input text is selected. Selection clearing therefore checks the active input/textarea range before stopping speech. Open-shadow active controls are followed through accessible shadow roots. No value, selection range, cursor or event default is changed by the reader. Selection-to-speech also works on normal title text and links added by dynamic pages; it does not force text selection on sites that suppress it or prevent link navigation. YouTube-specific behavior has not been manually verified.

Input regression fix: when a selection drag ends outside its field, the release event's path does not contain the input. The reader now falls back to the focused native control instead of discarding that selection. Pointer-release and selection-key listeners run in capture phase so normal bubbling `stopPropagation()` handlers in page widgets do not hide those events. Regression tests cover a real mouse drag ending outside the field and a native input that stops pointer/key event propagation; earlier tests covered keyboard selection only and missed these cases.

The default voice option is **Auto-detect language** (`voiceName` empty or omitted). Chrome's built-in `i18n.detectLanguage()` detects each new selection. Reliable results with a dominant language choose an exact installed voice locale first, then another local voice of the same language. An explicit installed voice overrides detection. If detection is uncertain, the reader checks for predominantly Thai, Hangul or kana text, then the selected element's declared `lang` through its ancestors (including open shadow hosts). Shared scripts such as Latin, Cyrillic, Arabic or Han are not guessed. If those hints are absent, reading uses a browser-language local voice when possible, otherwise the first local voice, with an uncertainty notice. Missing matching local voices produce an install/manual-choice message instead of silently reading in the wrong language. Chrome's initially empty platform voice list is retried after voices change or a bounded 1.5-second wait. Detection is once per selection, not sentence-by-sentence switching within a mixed-language selection. Stop cancels pending detection, and no new app dependency, permission or server is introduced.

`selection-reader.js` attaches delegated listeners to each injected frame document, so new text needs no rescanning or observer. Open-shadow selection uses the available shadow selection API where supported. Cross-origin frames require separate permitted injection; protected pages, canvas/PDF text and inaccessible shadow selections remain unsupported. Disabling removes listeners, pending timers and the status panel. The site's Selection, DOM text, event handlers and input values are preserved. Speech controls never prevent the site's keyboard/pointer events.

`selection-tts.js`, imported by the existing classic service worker, validates extension senders, saved opt-in, the tab's active state, text length and request IDs. Generation tokens cancel delayed speech after Stop or a newer selection. Only the owning frame/document can stop its reading through a page message. Status replies contain no selected text. Voice/speed are stored under `settings.dyslexia.speech`; global enable and the listening experience gate the feature. The existing `tts` permission is reused.

Verification:

```powershell
npm.cmd run build
node --test tests/extension.test.js tests/dyslexia.test.js tests/dyslexia-settings.test.js tests/read-aloud.test.js tests/selection-tts.test.js
node tests/compatibility.browser.mjs
```

The speech unit tests mock Chrome TTS and check local voices, saved speed, disabled/background cases, length limits, missing voices, document ownership, navigation, and cancellation during voice loading. Real-Chrome scenarios check trusted selection events and message delivery, partial input selection, multiline textarea selection, open-shadow inputs, preservation of values/ranges, suppression of programmatic/password/payment selections, dynamic title links, Escape and disable cleanup. Chrome TTS is mocked in those browser scenarios: actual audible output, voice availability and service-worker lifecycle during long utterances still need an installed-extension check. Reload the extension and target pages after updating `dist`, enable listening, save, select a short paragraph, then test Escape and a second selection.
